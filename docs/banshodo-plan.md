## 2. 共通化できるシステム（作品に依存しない部分）

1. **占術エンジン**（DOM を使わない純粋な関数。node でも試験できる）
2. **占術の登録の仕組み**（1占術を1ファイルにする。追加するときに中心部を書き換えない）
3. **統合エンジン**（結果を共通の形にして、一致と食い違いを出す。決定論的に動く）
4. **記録（運命の書、鑑定の履歴、人生年表、手相の写真）**
5. **占いの画面**：重ね画面の部品。作品は「店の設定」を渡すだけで開ける。
6. **今日のテーマを渡す仕組み**：ゲームのイベント条件として使う。

作品ごとに変えるのは、店の設定（外観、店員、会話、BGM、演出、限定メニュー、限定イベント）だけにする。

### 天体の計算
- 星座の境目、九星と四柱推命の節入り、ホロスコープには、天体の位置の計算が要る。
- 第一候補は **astronomy-engine**（MIT ライセンス、依存なし、約 200KB）。
  - 版を固定して `vendor/` に同梱する。
  - 精度は ±1 分角ほどで、占いには十分。
  - 入れるかどうかは制作者が決める（10章）。
- 入れない場合は、1900〜2100 年の節入りの表（JSON）を作って持つ方法もある。

### 手相
- 線の位置を、写真から正確に自動で読み取れる既成の仕組みは無い。
- そこで、**本人が確かめて直す**流れを基本にする。
  1. 写真を登録する。左右は自動で推定するが、本人が「左・右」を選び直せる。
  2. 写真の上に、線の候補を表示する。候補の出し方は、写真の明暗の簡単な解析か、本人がなぞるか、AI の画像認識（本人が同意したときだけ）。
  3. 本人が線の種類を決める（生命線、知能線など）。消す・足すもできる。
  4. **確定した線だけ**を計算に使う（長さ、始点、終点、交差、分岐）。決まった解釈の表から鑑定する。
  5. 線を読み取れない、または候補を確定していない場合は、「読み取れない」と表示する。推測で鑑定しない。
- 写真は端末の中（IndexedDB）に保存する。
  - 送ってよいのは、本人が送ると選んだときだけ。
  - 時期の違う写真を並べて比べる。

## 5. AI と通常のプログラムの役割分担

| 役割 | 担当 | 理由 |
|---|---|---|
| 暦、干支、星、九星、数、画数、抽選 | **通常のプログラム**（決定論的） | 同じ入力と同じ流派なら、同じ結果になる。試験もできる |
| 占術ごとの基本の解釈 | **通常のプログラム**（解釈の表。文はオリジナル） | どの占術のどの要素から出た解釈かを、必ず示せる |
| テーマ（創造性・挑戦・対人など）への変換と、一致・食い違いの判定 | **通常のプログラム**（決まった語彙と、反対の組み合わせの表） | AI に任せると、在りもしない一致を作るおそれがある |
| 総合鑑定の文章、言い回し、質問への答え | **AI** | 下の決まりのとおり |
| 手相の線の候補 | AI か画像処理。**確定は本人** | 線を言い切らない |
| 夢占いの解釈の補足 | AI（辞書の結果も添える） | ― |

### AI の決まり（捏造を防ぐ）
1. AI に渡すのは、統合エンジンの出した**構造データだけ**にする。
   - 占術、要素、テーマ、出典、一致、食い違い。
   - 生年月日、名前、写真は渡さない。
2. AI の出力も構造化する（文、出典の ID）。
3. **検査器**が、出典の ID が入力に在るかを確かめる。在りもしない占術、線、数が出てきたら、その文を捨てる。
4. AI が使えないときは、テンプレートの文で総合鑑定を出す。オフラインでも遊べるようにする。
5. どの文にも「この占術のこの結果から」と出典を表示する。「娯楽です。医療・お金・法律の判断に使わないでください」を常に表示する。

### AI の呼び方
- ゲームは静的サイトなので、API の鍵をブラウザに置けない。
- サーバーで中継する（Cloudflare Workers か Supabase Edge Functions。どちらも無料枠がある）。中継側では次のことをする。
  - 鍵を持つ。
  - 1人1日あたりの回数を制限する。
  - 入力を検査する（構造データだけを通す）。
- AI の利用料がかかる（使う量による）。誰が払うかは制作者が決める（10章）。

## 7. API の設計（ブラウザの中の JS モジュール）

```js
import Bansho from './banshodo/index.js';
Bansho.methods.list()                       // 使える占術だけ（作りかけは返さない）
Bansho.methods.register(def)                // { id, name, needs:[...], schools, compute(profile, opts) → Result }
Bansho.run(methodId, person, {school, seed, date}) → Result
Bansho.integrate(results) → Synthesis       // 決定論的
Bansho.today(person, date) → { themes, luck } // ゲームのイベント条件用
Bansho.book.save(reading) / list() / get(id) / remove(id) / clearAll()
Bansho.open(shop, { onClose })              // 重ね画面を開く。閉じたら onClose(result) でゲームへ戻る
```

店の設定（作品ごとに用意する）：
```js
{ id:'kaidan-corner', game:'dannoura-village', brand:'万象堂',
  npc:{ name, portrait, voice, lines:{ greet, menu, bye, … } },
  theme:{ palette, bg, bgm, sfx, effects:'mist' },
  menu:['today','tarot','birth','east','west','love','work','age','synth','book','history'],
  extraMethods:['kaidan-omikuji'], events:{ onTheme:{ creativity:'workshop_recipe' } } }
```

サーバーの API（後の段）：
- `POST /bansho/synthesize`：入力は Synthesis の構造データ、出力は出典つきの文。
- 記録の同期は Supabase の REST と RLS を使う。

## 8. 画面・NPC との連携の方法

1. NPC に話しかける。各作品の会話の仕組みが `Bansho.open(shop)` を呼ぶ。
2. 重ね画面（DOM）が開く。ゲームの側は止める（ミニゲームの枠と同じ）。
3. 鑑定が終わる、または閉じる。`onClose` でゲームへ戻る。鑑定の記録と今日のテーマを返す。
4. ゲームは、テーマをイベント条件として使う（例：`creativity` なら工房のレシピを出す）。
   - **占いで本筋が止まらない**ように、条件は「足すだけ」にする。必須の分岐には使わない。

作品の形ごとの使い方：

| 作品の形 | 使い方 |
|---|---|
| ブラウザの 2D / 3D（canvas、three.js） | そのまま `Bansho.open` を使う |
| Unreal（UE5）など、ブラウザ以外 | 計算の部分は JSON の仕様と答えの表があるので、移植できる。画面は作品の側で作る。<br>**作品の形が分かってから決める** |

### メニューの出し方
- 指示書の12項目のうち、**使える占術だけ**を出す。
- 作りかけの占術は出さない（「準備中」とも出さない）。

## 10. 既存システムへの影響とリスク

### 影響
- 段1〜5は、新しいフォルダ（`banshodo/`、`tests/banshodo-*`）と新しい鍵だけを使う。
  - **既存のゲーム、セーブ、エンディングには触れない。**
- `sw.js` は、新しいファイルをキャッシュの対象にするかどうかと `VERSION` だけを変える。
  - AI の API の応答はキャッシュしない。

### リスク

| リスク | 内容 | 対策 |
