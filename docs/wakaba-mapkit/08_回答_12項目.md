## 1. 追加できる機能（このリポジトリに足せるもの）
すぐ足せる（クラウドの Claude だけで作れる・`03` の〔C〕）：
- 高さマップの地形（山・坂・谷）と、坂を歩ける当たり判定
- 種つきの配置（木・岩・家）と、**入口・道を塞がない／浮き・めり込み・重なりを見つける／全ての目的地へ歩いて届く**の自動検査
- PBR 材質・圧縮テクスチャ（KTX2）・ライトマップの読み込み、夕暮れ・高さの霧・雨で濡れた地面・懐中電灯の影
- 画質の段 `ultra`（RTX 3060 Ti 級）と、実機で fps を記録する仕組み
- 素材の目録（メタデータ）とライセンス門（不明な素材を止める）
- 日本語の指示 → 地図仕様 JSON → 配置 → 検証レポート の流れ
- これらを `mapkit/` として作品から切り離し、境界侵食や今後の作品で共通に使う

利用者の PC が要る（〔S〕〔M〕）：Gaea・Blender での素材づくり、光の焼き込み、実機での見た目と fps の確認、UE5 で作る場合の全部。

## 2. 外部ソフト（何を使うか）
| 役割 | 第一候補 | 代わり | 理由 |
|---|---|---|---|
| 地形 | **Gaea**（書き出しが 1024 で足りる試作は Community、商用なら Indie） | Blender の地形（手続き）・自作のノイズ | 侵食のリアルさは Gaea が強い。ただし Community は非商用 |
| モデル・焼き込み | **Blender**（5.2 LTS か 4.5 LTS） | – | 無料・Python で自動化できる・glTF/FBX/USD を書き出せる |
| 素材 | **Poly Haven・ambientCG（CC0）**＋自作 | Fab（UE の PC 版だけで使うのが安全） | Web で配っても問題が起きにくい |
| ゲームの実行 | **Three.js（既存）** | UE5（PC 版を作るなら） | 既存の仕組み・試験・スマホ・Pages がそのまま使える |
| 自動化 | Claude Code＋Git の PR（＋後で n8n） | – | 最初は PR だけで足りる |
| 画像生成 | 利用者の ComfyUI（既存の依頼書あり） | わかばシステム（中身未確認） | テクスチャの下絵・看板・汚れの絵など |

## 3. 無料でどこまでできるか
- **完全に無料で最後まで作れる**：Three.js＋Blender＋CC0 素材＋（地形は Blender か自作のノイズ）＋n8n の自己ホスト＋GitHub Pages。
- 無料だが条件つき：
  - Gaea Community＝**非商用のみ**・書き出し 1024×1024（検証マップ 256m 四方なら 1 ピクセル 25cm で足りる）。作品で収益を得るなら Indie（$99・年商 10 万ドル未満）【検索要約】。
  - Unreal Engine＝無料で使え、製品の生涯総収入 100 万ドルを超えた部分に 5%。
  - Fab の無料素材＝Fab Standard License（Web で生の素材ファイルを配ることの扱いは未確認）。
  - n8n＝自分の制作のための自己ホストは無料（n8n 自体を他人に提供しない限り）。
- 有料になりうるもの：Gaea Indie 以上、Megascans の大半（2025 年から有料）、Codex／Grok の利用料（プラン・従量）、メモリの増設（32GB 推奨）、NAS。

## 4. Claude Code が自動で操作できる範囲
| できる | 条件 |
|---|---|
| コード・地図仕様・スクリプト・文書を書く、試験を走らせる、PR を作る | このクラウドで今できる |
| ブラウザ（ソフト描画）で歩かせて検証・画面撮影・描画呼び出しの計測 | 今できる（fps は参考にならない） |
| bpy（Blender の Python モジュール）で .blend の生成・glTF 書き出し | PyPI から入れれば**クラウドでも可能**（今は入れていない）。GPU の焼き込みは CPU の Cycles で遅いが可能（未検証） |
| glTF の最適化・検証（gltf-transform・gltf-validator） | npm で取れる。素材がクラウドに届けば可能 |
| 利用者の PC の Blender／UE を直接操作 | **利用者の PC で Claude Code を動かした時だけ**（Blender Lab の MCP・Epic の Unreal MCP〔実験的〕・UE の Python／Remote Control）。このクラウドからは届かない |
| Gaea の操作 | Gaea.Build.exe（コマンドライン）で既存の .tor を書き出すことは自動化できる見込み（どの版で使えるか未確認）。**地形のノードを組む作業は人** |
| 素材サイトから素材を取る | **できない**（このクラウドは通信がブロック）。利用者の PC なら Poly Haven の API などで可能（未確認） |
| 素材の購入・ライセンスの判断・見た目の最終判断 | **しない**（人が行う） |

## 5. n8n で自動化できる範囲
- 依頼の受付（フォーム・チャット）→ 仕事のファイルを作る → Claude Code をヘッドレスで呼ぶ（`claude -p`・利用者の PC）→ PR ができたら利用者へ通知 → 承認を待つ（待機ノード）→ マージの後に書き出し・最適化・検証のスクリプトを走らせる → 結果を通知。
- 夜間に重い書き出し（Gaea のビルド・Blender の焼き込み）を並べて順に走らせる（GPU の仕事は 1 つずつ）。
- **できない／させないこと**：見た目の良し悪しの判断、ライセンスの判断、承認の代行。n8n が壊れても Git の状態が正本なので作業は止まらない設計（`07` §8）。
- n8n の有無・版は利用者の PC で**未確認**。

## 6. Blender・Gaea・UE の受け渡し
| 物 | 形式 | 注意 |
|---|---|---|
| 地形の高さ | **16bit PNG**（Three.js・UE どちらも）／RAW（.r16・UE の Landscape）／EXR（32bit 浮動小数・精度が要る時） | 8bit PNG は段々になるので使わない。高さの範囲（最小・最大 m）を必ず別に記録。UE の Landscape は推奨の大きさ（例 1009・2017 など）に合わせる |
| 地形のマスク（草・岩・流れ） | 8bit PNG | 地面の塗り分けに使う |
| 建物・岩・木 | **glTF 2.0（.glb）**＝Three.js 向け／**FBX**＝UE 取り込みの定番／**USD**＝UE・Blender・Gaea 3（Pro）の共通の器（試す） | 単位は m、上は Y（glTF）／Z（UE・Blender）。書き出しの設定を固定した bpy スクリプトで揃える |
| 材質 | PBR の画像（色・法線・粗さ/金属/AO を詰めた ORM） | UE の複雑な材質は glTF にそのままは出ない（公式の glTF Exporter は「焼き込み」で対応）。**材質は Blender 側を正本**にするのが楽 |
| 光 | Blender でライトマップを焼いて glTF の第 2 UV に | UE の Lumen の光はそのままブラウザへ持っていけない |
| UE → ブラウザ | UE の glTF Exporter（レベル・静的メッシュ・材質の焼き込みに対応）【検索要約】 | Nanite の超高ポリはブラウザで描けない＝LOD を作り直す必要がある |

## 7. AI 自動生成の現実的な限界（正直に）
- **日本語 → 配置**：配置の数値（どこに何を何個）は AI が十分に作れる。ただし「怖い」「寂しい」などの雰囲気が出ているかは、AI が数値で確かめられない＝**人の目が要る**。
- **3D モデルの自動生成（画像 → 3D）**：TRELLIS.2 は商用可（MIT）だが VRAM 24GB 級、Hunyuan3D は地域制限つきの独自ライセンスで、8GB で動くのは小さい版だけ【検索要約・未確認】。**建物の部品のように寸法が決まった物は不向き**（寸法・原点・当たりが合わない）。岩・小物の下書きなら使える可能性。
- **建物**：寸法の規格どおりの部品を bpy で「箱から作る」のは AI がスクリプトで書ける。しかし**写実に見える汚れ・欠け・質感は人の仕上げか、良い CC0 素材が必要**。
- **地形**：Gaea のノードの組み方を AI が自動で組むのは難しい（ファイル形式・API が公開されているか未確認）。手続きのノイズなら AI が作れるが、侵食のリアルさは Gaea に劣る。
- **見た目の比較**：画面撮影と条件の照合は「霧がある」「家が 3 軒見える」程度まで。写実の良し悪しの判断は人。
- まとめ：**AI は「配置・規則・検査・スクリプト・書き出しの自動化」に強く、「質感・雰囲気・最終判断」は人**。最初の検証マップは「AI が組んで人が直す」前提で計画しています。

## 8. RTX 3060 Ti（8GB）で実現できる品質
| 方式 | 見込み（未実測） |
|---|---|
| ブラウザの Three.js（WebGL2） | 256m 四方の山の廃村：PBR＋焼いた光＋霧＋影 1〜2 灯で **1080p 60fps は十分狙える**。写実の度合いは「焼き込みのきれいな PC ゲーム（2015 年前後）」くらいが現実的。リアルタイムの GI・大量の動的な光・超高ポリはできない |
| UE5 | Nanite＋Lumen（ソフト or Lite）＋TSR で、**1080p・高設定 60fps 前後**が見込み。森の密度・霧（ボリューメトリック）で落ちる。VRAM 8GB は高解像度テクスチャを多用すると足りなくなる |
| エディタ作業 | **メモリ 16GB が一番の弱点**。UE のエディタは推奨 32GB（Epic の表）。Blender や ブラウザと同時は苦しい。SSD 512GB も UE＋素材で圧迫 |
- 実測が無いので、フェーズ 3 で `?perf=1`（ブラウザ）と `stat unit`（UE）の数字を取り、`07` §6 の段を直します。

## 9. 最初の検証マップ（山の廃村）の具体的な手順
（案 A の場合。各手順に担当）
1. 〔M〕`09` のチェックリストに答える（PC・ソフトの有無・画風・公開範囲・収益化）。
2. 〔C〕地図仕様 `maps/haison/map.spec.json`（`07` §5.2）を作り、利用者が確認。
3. 〔C〕仮の地形（手続きのノイズ）と灰色の箱の家・円柱の木で、配置・検査・歩く試験まで通す（フェーズ 2）。
4. 〔S/M〕地形：Gaea（Community で 1024 の 16bit PNG）か Blender で高さマップを作り、`maps/haison/heightmap.png` に置く。高さの範囲を記録。
5. 〔S/M〕建物の部品：Claude が書く bpy スクリプト（規格どおりの壁・床・扉・窓・屋根の箱）を利用者の Blender で実行 → 人が汚れ・破損を仕上げ → glTF 書き出し（スクリプト）。
6. 〔M〕CC0 素材を取得：森の地面・苔の岩・木の板・土壁・瓦の PBR、夕暮れの HDRI、木と岩のモデル（Poly Haven・ambientCG）。メタデータを書き、`verifiedBy` を利用者が記入。
7. 〔S〕Blender でライトマップを焼く（スクリプト）。
8. 〔C〕取り込み・最適化（KTX2・Meshopt）・PBR・霧・夕暮れ・懐中電灯・`ultra` の段。
9. 〔C〕検査とレポート、Playwright で歩く試験。
10. 〔M〕利用者の PC で fps を測り、10 分遊んで「探索できるか」を判断。直す所を指示。
- UE の短期の試し（任意・2 週程度・利用者の PC）：同じ高さマップと部品の FBX を UE 5.8 に入れ、Landscape＋Lumen Lite＋霧で 1080p の fps と見た目をブラウザ版と比べる。**ここで案 A のままか、C へ進むかを決める材料にする**。

## 10. 他のゲームへの展開
- 共通にするもの：`mapkit/`（地形・配置・検査・描画の部品）、素材ライブラリ（目録とライセンス門）、地図仕様の形、検証レポート、画質の段。
- 作品ごとに持つもの：物語・敵・保存・画風（トゥーン or 写実）・地図の中身。
- 展開の順の案：境界侵食の別区画（山・廃村）→ 境界侵食の町の写実版（任意）→ 新作。トビネズミ（2D）や本編（2D）には直接は使わないが、**素材の目録とライセンス門は 2D 素材にも使える**。
- 部品の型（`jp_house_abandoned` など）を増やすほど、新しい作品で使える「指示 → 地図」の幅が広がる。工場・研究所・学校・病院・倉庫・地下は、同じ格子の規格で部品を足していく。

## 11. 方式の選択：A／B／C（推奨と理由）

| | **A：ブラウザの Three.js を本番**（UE5・Blender・Gaea は制作の道具。glTF＋焼いた光で書き出す） | **B：UE5 のデスクトップ版に移る**（高性能 PC 向け） | **C：両方**（UE5 で高品質の PC 版、Three.js で Web・スマホ版。素材ライブラリは共通） |
|---|---|---|---|
| 遊べる端末 | PC・スマホのブラウザ（今と同じ） | Windows PC だけ（スマホ・ブラウザで遊べなくなる） | 両方 |
| 見た目 | 良い（焼き込みの写実）。UE には届かない | 最高（Lumen・Nanite） | PC 版は最高、Web 版は A と同じ |
| 既存の資産 | **全部使える**（境界侵食・試験・保存・PWA・Pages） | ゲームの仕組みを**全部作り直し**（C++/ブループリント）。物語・戦闘・保存・試験・作品間の連携もやり直し | 両方を保守（二重の手間） |
| 配布 | GitHub Pages（無料・URL を送るだけ） | 数 GB のパッケージ。配る場所（Steam・itch.io 等）・署名・更新の仕組みが要る | 両方 |
| AI での自動化 | Claude がクラウドで直接作って試験できる | 利用者の PC でしか動かない（クラウドの Claude は試験できない） | Web 側は A、PC 側は B |
| 費用 | 無料 | 無料（収入 100 万ドル超で 5%）＋配布の費用 | 同上 |
| 必要な PC | 今の PC で十分 | 32GB 推奨（今は 16GB） | 同上 |
| 危険 | 写実の上限 | 作り直しの量が大きい・スマホを失う・クラウドで検証できない | 手間が 2 倍・中身のずれ |
| 移行の手間（目安） | 小（足すだけ） | **大**（境界侵食の 8 フェーズ分の作り直し相当） | 大＋継続 |

### 推奨：**まず A。UE5 は「試し」と「素材づくりの道具」として使い、C に進むかは試しの結果で決める**
理由：
1. 依頼の最重要条件は「**きれいなだけでなく、ゲームとして探索できること**」。当たり・歩ける・道案内・敵の追跡・保存・試験は**すでに Three.js 側にある**。UE に移るとこれを作り直す間、探索できる物が出てこない。
2. `DECISIONS.md`（2026-10-14）で「Three.js・ブラウザ・PC 優先・スマホは試しながら（無理ならスマホだけ方向性を変える）」と決まっている。A はこの決定の延長。
3. クラウドの Claude が**自分で作って自分で試験できる**のは A だけ（UE は利用者の PC でしか動かない）。AI 自動化の基盤としても A が有利。
4. 素材ライブラリ・地図仕様・検証の形は A でも C でも同じなので、**A で始めても C に進む時に無駄にならない**。
5. 今の PC（メモリ 16GB）は UE のエディタには不足気味。C に進むならメモリ 32GB への増設を先に勧めます。

C に進む目安（試しの結果で判断）：
- UE 版の見た目の差が大きく、かつ「PC 専用版」を出す価値があると利用者が判断した時
- 利用者が UE のブループリントを自分で触れる時（AI だけでは UE 側の遊びの部分の検証ができないため）

B（UE だけに移る）は、スマホ・ブラウザを捨ててよく、作り直しの期間を受け入れられる場合だけ。**現時点では勧めません**。

### もう一つの分かれ道：画風
境界侵食は「アニメ調（トゥーン＋輪郭線）」で決定済み。写実の山の廃村は、
- (i) 境界侵食とは**別の試験用のマップ**として作る（`mapkit.html`）、
- (ii) 境界侵食の一部（例：異界・山の区画）だけ写実にする、
- (iii) 境界侵食全体を写実に変える、
のどれにするか、利用者の判断が必要です（Q-A1）。フェーズ 2〜4 は (i) で進め、本編に入れるのは判断の後にします。
