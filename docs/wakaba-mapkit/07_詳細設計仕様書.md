- 共通部品を `shinshoku/` から移す時は、**元の場所は import し直すだけ**にして二重の実装を残さない。
- **実装の記録（フェーズ 1・2026-10-17）**：charkit `14` §2 と置き方がずれていた所を、次の 1 つの形にそろえた（charkit `14` にも同じ記録）。
  - JSON スキーマの検査は **`mapkit/core/schema.js` の 1 つだけ**（charkit `14` の `charkit/core/validate.js` は、この共通の検査を使ってキャラクター・モーションの中身を見る係にした）。スキーマの一覧と登録簿は `mapkit/core/schemas.js`、node 専用の助けは `mapkit/core/node.mjs`。
  - スキーマの正本は**コードと一緒**：`mapkit/schema/asset-meta.schema.json`（`$id` は §2 のとおり `wakaba-assets/asset-meta.schema.json` のまま）・`map-spec.schema.json`・`map-report.schema.json`、`charkit/schema/*.json`。素材ライブラリ（§2）の場所が決まっても動かさない。§2 の `wakaba-assets/schema/` は作らない。
  - ライセンス門は**規則（純粋関数）`mapkit/assets/gate.js`＋CLI `mapkit/assets/license-gate.mjs`** に分けた（ブラウザでも規則を使えるように）。charkit `07` §4 の権利の規則も同じ `gate.js` に入れた（門は 1 つ）。
  - レポートは `mapkit/report/report.js`（形・検査・md への変換の純粋な部分）。ファイルへの書き出し（json・md・画像）はフェーズ 2 の `tools/mapkit/build_map.mjs` で行う。
  - CLI は `tools/mapkit/validate_spec.mjs`（地図仕様・レポート）を足した。試験のファイル名は `tests/wakaba-mapkit-*.test.mjs`・`tests/wakaba-charkit-*.test.mjs`（charkit `14` §6 の `charkit-*.test.mjs` から変更）。
  - 作品の条件（商用か・配信先・使う物）と素材ライブラリの場所は `wakaba.config.json`（リポジトリの根）。
  - `sw.js`：境界侵食の `bones.js` が `charkit/rig/bonemap.js` を読むようになったので、`charkit/`・`mapkit/` の `.js` をネット優先（`shell`）で保存する振り分けを足した（スキーマの JSON・`.mjs` は扱わない）。
- 既存の `vendor/three-esm/` に KTX2Loader・Basis の変換器・MeshoptDecoder を**版固定で**足す（`vendor/three-esm/README.md` と同じ書き方で SHA-256 を記録）。

## 2. 素材ライブラリの置き場所

**原則：原本（重い・ライセンスの制限がある）は Git に入れない。ゲームで使う軽い書き出しと目録だけ Git。**

```
wakaba-assets/                  ← 新しい Git リポジトリ（private 推奨）。目録と小さなプレビューだけ
  catalog.json                  全素材の目録（下のスキーマの配列。生成物＝meta.json から作る）
  schema/asset-meta.schema.json
  entries/<category>/<id>/meta.json
  entries/<category>/<id>/preview.webp      256px の見本
  licenses/<id>.txt|pdf                     購入の証明・ライセンス原文の写し（再配布可の物のみ。不可なら場所だけ記録）
  quarantine/                               ライセンス門で止まった物の meta.json
NAS:/wakaba/assets-src/<category>/<id>/     原本（.blend .tor .exr 原寸テクスチャ・購入物）
NAS:/wakaba/assets-out/<id>/<version>/      書き出し（glb・ktx2）
各作品のリポジトリ/assets/3d/<id>.glb        実際に配信する物（CC0・自作・再配布可の物だけ）
```
- NAS が無い場合：外付け SSD＋クラウドのストレージ（利用者の選択）。**Git LFS は「書き出し」にだけ使う案**もあるが、GitHub の LFS の無料枠（容量・転送量）は**未確認**のため、使う前に確認（Q-B2）。
- 公開リポジトリ（dannoura-game）には Fab・購入物の原本・書き出しを**置かない**（`04` §3）。
- **フェーズ 1 の実装**：置き場所（Q-B2）が未定のため、仮に**このリポジトリの `wakaba-assets/`**（`catalog.json`・`entries/`・`quarantine/`）を `wakaba.config.json` の `assetLibrary` で指している。今は 0 件（試験用の作り物は `tests/fixtures/wakaba/` に置き、目録には入れない）。移す時は `assetLibrary` を書き換えるだけ。

### 3.1 ライセンス門（license-gate）の規則
| 条件 | 結果 |
|---|---|
| `license.id` が `unknown`、または `commercial` が `unknown` | **止める**（quarantine）。自動では使わない |
| `verifiedBy` が空 | 止める（人が確認するまで） |
| `commercial` が `no` で、作品が商用（作品の設定 `commercial: true`） | 止める |
| 配信先が Web（公開）で `redistributeRaw` が `no` / `unknown` | **Web の書き出しに入れない**（UE の PC 版だけ可） |
| `engines` に配信先のエンジンも `any` も無い | 止める |
| `source.type` が `ai_generated` で `aiModel` が空 | 止める |
| `attribution` が空でない | 通すが、クレジット表（`credits.json`）に自動で足す |
| `regionLimit` がある | 止めて人に確認 |
- フェーズ 1 の実装で足した規則：`status` が `quarantine`／`retired` は止める（`STATUS`）・Mixamo／Fab の物は `redistributeRaw` の記入に関係なく公開の Web には入れない（`KNOWN_NO_WEB`・Fab の Web 配信の扱いが未確認のため）・作品が使うと書いた物が目録に無ければ止める（`MISSING`）・`engines` が書いていない物は「どのエンジンも無い」と同じ扱い。撮影の元（`motion_source`）は配らないので Web・エンジンの規則は当てない。作品の商用が「未定」（`"unknown"`）・未記入は商用と同じ扱い。
- 出力：`license-gate.json`（素材ごとに pass/block と理由）。CI（`node tests/run.mjs`）で、作品が参照する素材が全部 pass でないと失敗にする。

## 4. 手続きの配置（PCG）の規則

### 4.1 種
- マップの種 `seed`（文字列）。層ごとの子の種は `hash(seed + ':' + layerId)`。**層を足しても他の層の配置は変わらない**。
- 同じ仕様＋同じ種＋同じ素材の版 → 同じ配置（試験で保証）。

### 4.2 層の順番
1. 地形（高さ・川で削る）→ 2. 道（スプライン → 平らにする・幅）→ 3. 建物（区画 → 間取り）→ 4. 立入禁止の形を作る → 5. 大きい物（崖の岩・大木）→ 6. 小さい物（下草・小石・落ち葉）→ 7. 演出（灯り・霧の塊）→ 8. 検証。

### 4.3 立入禁止（keep-out）
| 形 | 既定 |
|---|---|
| 扉の前 | 扉の外向きに 幅（扉の幅＋0.6m）× 奥行 2.0m の箱。室内側も 1.2m |
| 道・山道 | スプラインの両側に 幅/2＋0.5m（下草は 0.2m まで許す＝`allowSmall`） |
| 祠・目的地の前 | 半径 2.5m |
| 出入口（マップのスタート） | 半径 4m |
| 崖の縁 | 縁から 1m は大きい物を置かない（落下の処理と見通しのため） |

### 4.4 建物のモジュール規格
- 格子 **0.5m**、壁の厚さ 0.15m、階高 **2.7m**（和室の天井高を想定・要調整）、扉 0.9×2.0m（和風の引き戸 1.8×1.8m も）、窓の下端 0.9m。
- 部品の原点：**格子の角・床の高さ**（`pivot: grid_corner`）。向きは +Z が外。名前の規則 `bld.<様式>.<部位>_<幅>x<高さ>_<変種>`（例 `bld.jp_house.wall_plaster_2x1_broken`）。
- 当たり：部品ごとに簡単な箱（`collision: box`）を glTF の別のノード（名前の頭に `COL_`）で持つ。Three.js 側は `collide.js` の箱に変換。
- 印（charkit `05` §2 の提案を採用）：扉・座る所などの**空ノードを名前の頭 `ANC_`** で部品に置き、組み立ての時に地図仕様の `anchors`（`auto: true`）を作る。`anchors` の欄はフェーズ 1 で `map-spec.schema.json` に入れた。

### 4.5 検査（validate）
| 検査 | 方法 | 既定のしきい値 |
|---|---|---|
| 浮き | 物の底の四隅（または底面の数点）の下の地面の高さとの差 | 差 > 0.05m（岩は 0.15m） |
| めり込み | 同上 | 差 < −0.30m（意図した埋め込みは `embed: 0.4` で許す） |
| 重なり | 当たりの箱（OBB）の交差。`overlapOk` の組み合わせは除く | 体積の 5% 超 |
| 坂 | 置く所の傾き | 建物 8° まで（土台で吸収）、木 35°、岩 60° |
| 入口の確保 | 立入禁止の形と当たりの箱の交差 | 0 件 |
| 到達 | 歩ける格子（0.5m・坂 35° まで・段差 0.4m まで）でスタートから BFS | 全目的地に届く・最短の道のり／直線の比 < 4 |
| 室内 | 入れる家：扉から全部屋に届く・天井高 ≥ 2.0m | – |
| 落下 | 崖の縁の格子から外へ出られない（見えない壁 or 落下の扱い） | 0 か所（または意図した所だけ） |
| 予算 | 描画呼び出し・三角形・テクスチャの量（画質の段ごと） | §6 |
- 失敗は配置をやり直す（種を `seed+'#retry'+n` に変えて最大 8 回）か、その物を外して報告。**黙って消さない**（レポートに出す）。

## 5. 地図仕様（日本語の指示 → JSON）

### 5.1 流れ
1. 利用者の日本語の指示 → Claude が `tools/mapkit/spec_from_prompt.md` の手順で **地図仕様 JSON** を書く（あいまいな所は `questions` に入れて利用者に聞く。勝手に決めた所は `assumptions` に書く）。
2. `build_map.mjs` が仕様を検証 → 必要素材の一覧（`needs`）→ 目録から検索 → 足りない物を `gaps` に → 配置 → 検査 → レポート。
3. `gaps` は**生成計画**（bpy の雛形・依頼文・CC0 の候補の探し方）として出すだけ。購入・生成 AI の実行は承認の後。

## 6. 画質の段（RTX 3060 Ti 8GB・i7-9700・16GB を「ultra」の基準に）

### 6.1 Three.js（案 A）
既存の `high/mid/low` に `ultra` を足す。数値は**目標**で、実機の計測で直す（フェーズ 3）。
| 項目 | ultra（3060 Ti・1080p） | high（既存 PC） | mid | low（スマホ） |
|---|---|---|---|---|
| 材質 | PBR（色・法線・ORM）＋ライトマップ | PBR＋ライトマップ（法線は近くだけ） | 色＋ライトマップ | 色だけ（または既存のトゥーン） |
| テクスチャの最大 | 2048（地面 4096 の塗り分け） | 2048 | 1024 | 512 |
| 影 | 太陽 2048×（カスケード 2）＋懐中電灯 1024 | 1024 | 512 | なし（焼き込みのみ） |
| 霧 | 高さの霧＋遠景の霞 | 同 | 距離の霧 | 距離の霧 |
| 描画呼び出し | ≤ 400 | ≤ 250 | ≤ 160 | ≤ 120（既存の基準） |
| 三角形 | ≤ 150 万 | ≤ 80 万 | ≤ 40 万 | ≤ 20 万 |
| テクスチャの量（GPU） | ≤ 1.2GB | ≤ 800MB | ≤ 400MB | ≤ 150MB |
| 草 | インスタンス 5 万本・60m まで | 2 万本・40m | 5 千本 | なし |
| 後処理 | トーンマップ・SSAO（軽）・ブルーム・色調 | トーンマップ・ブルーム | トーンマップ | なし |
| 目標 fps | 60（最低 45） | 60 | 30〜60 | 30 |

### 6.2 UE5（案 B／C の時）
RTX 3060 Ti・1080p・目標 60fps の出発点（**実測で直す前提・未検証**）：
- Nanite：オン（岩・建物）。Nanite Foliage は実験的なので最初は使わない。
- GI：**Lumen（ソフトウェア）または 5.8 の Lumen Lite**、反射は Lumen の低め。ハードウェアのレイトレースは切る（8GB では重い）。
- 影：Virtual Shadow Maps。光が多い室内は MegaLights（5.8 で正式版との情報）を試す。
- アップスケール：TSR（または DLSS プラグイン・規約を確認）で 67〜77% 内部解像度。
- テクスチャのストリーミングの上限（プール）：VRAM 8GB に対して 3〜4GB から。
- World Partition：256m 程度の検証マップなら不要（使っても可）。
- エディタ：メモリ 16GB では Blender・ブラウザを閉じて使う。シェーダーのコンパイルが i7-9700（8 スレッド）で長い（初回は数十分〜時間の見込み・未計測）。

## 8. AI チームの仕事と鍵（n8n なしでも動く形）
- 仕事のファイル `jobs/<id>.json`：`{ id, title, assignee: "claude|codex|grok|user", branch, claims: ["mapkit/terrain/**"], needs: {gpu, vramGB, apps}, status: "queued|claimed|review|done|blocked", approvals: [] }`。
- **鍵の規則**：`claims` のパターンが他の `claimed`／`review` の仕事と重なったら、取れない（待つ）。仕事は必ず自分のブランチ（`job/<id>`）で行い、PR で合わせる。**main への直接の書き込みはしない**。
- 別の AI は**レビュー（コメント）だけ**を基本にし、同じファイルを編集しない。
- n8n を入れたら、n8n はこのファイルを読み書きするだけ（状態の正本は Git）。n8n が止まっても作業は続けられる。

## 9. バックアップと復元
| 物 | 正本 | 予備 1 | 予備 2 |
|---|---|---|---|
| コード・地図仕様・目録 | GitHub | 利用者の PC のクローン | NAS へ週 1 の `git bundle` |
| 原本（.blend・.tor・原寸テクスチャ） | NAS | 外付け SSD（週 1 の同期） | 別の場所（クラウドのストレージ等・任意） |
| 購入物・ライセンスの証明 | Fab 等のアカウント（再ダウンロード可）＋`licenses/` | NAS | – |
| UE のプロジェクト | NAS（Git LFS か Perforce は後で判断） | 外付け SSD | – |
| UE の派生データ（DDC）・中間ファイル | **バックアップしない**（再生成できる） | – | – |
- 復元の試験：フェーズ 3 で一度、空の PC（またはフォルダ）から「クローン＋NAS の原本」だけでマップを書き出し直せるかを確かめる。
- SSD 512GB の対策：UE の DDC・Fab の保管場所を外付けか NAS に移す（場所は利用者の PC で確認・`09`）。
